> # Pipe compared with a CLI pipe
> - CLI: `producer | consumer` connects producer stdout to consumer stdin.
> - Here: `_collect.pipe.send(dict)` → pipe → `MemorySession.pipe.recv()`.
> - Same message-channel idea; no stdin/stdout redirection here. Python serializes/reconstructs dictionaries.
> - `Pipe(duplex=False)` creates two ends in `__init__`: parent receives; child sends.
> - Parent passes the sending end to the child, then closes its own copy. Child's copy remains usable.
>    - **Me**: In the code it sounds as if it must close it's own copy in order for the child pipe to work properly: # The parent must close its copy so child exit becomes EOF on the read end.
>      - **Follow-up:** Sending works even while that parent copy is open. Closing it makes **child exit detectable**: otherwise the parent itself still holds a sending end, preventing EOF.
>    - **Me**: Why do we even save a copy of the child's pipe? (`self._child_pipe = child`). We already have it with self.pipe, don't we? And then we only close this copy for some reason? And we're even closing it on start and on finish?
>      - **Follow-up:** These are **different endpoints**: `self.pipe` receives; `child` sends. `self._child_pipe = child` saves another reference to the sending endpoint, not a newly created endpoint.
>      - **Follow-up:** `.start()` gives the child access to the sending endpoint. Only afterwards can the parent close its own handle; closing before startup would prevent passing a usable endpoint.
>      - **Follow-up:** The close in `finish()` also handles cleanup if startup never completed. Closing an already-closed connection is harmless; it does not close the child's separate handle.
> - `poll(timeout)` checks/waits for readability; `recv()` consumes a message. EOF means all sending ends closed.

> # Spawn: process, not thread
> - `get_context('spawn')` selects how multiprocessing starts children.
> - Creating `Process(target=_collect, ...)` prepares an object; `.start()` launches a fresh Python process running `_collect(...)`.
> - Runner, collector, and CU have distinct PIDs. CU workers remain threads inside the CU.
> - Session dictionaries stay in the runner; the child receives arguments and explicitly shared communication handles.
> 
> # Stop event and shutdown
> - Separate from the one-way pipe: session → collector through a shared event flag.
> - `.set()` requests stopping; `.is_set()` checks the flag; `.wait(timeout)` wakes on the flag or timeout.
> - A sleeping collector wakes, performs its next sample, sees the flag, then exits normally.
> - `.join(timeout=5)` waits for exit. If still alive, `.terminate()` requests forced termination, followed by another `.join()`.
> - Closing a pipe end releases communication resources; it does not kill a process.
> 
> # Clock offset and uncertainty
> - RSS timestamps and runner times use `CLOCK_MONOTONIC`; native operators use `high_resolution_clock`.
> - CU reads: monotonic-before → native-clock → monotonic-after, immediately before sending a response.
> - Monotonic anchor = midpoint(before, after); uncertainty = half their separation, rounded up to nanoseconds.
> - Example in seconds: native anchor 1012, monotonic anchor 12 → offset -1000. Native operator start 1010 becomes monotonic 10.
> - Thus durations stay unchanged; only the coordinate system changes. Assumes a stable clock relationship during the operation.
> - Uncertainty slightly widens allowed submission/arrival bounds. It neither identifies RAM ownership nor recovers missed memory spikes.
> 
> # Bisect and window boundaries
> - Example: timestamps `[0, 20, 40, 60]` ms; requested window `[25, 45]` ms.
> - `bisect_right(times, 25) - 1` → `lo = 1`, the sample at 20 ms.
> - `bisect_left(times, 45)` → `hi = 3`, the sample at 60 ms.
>   - **Follow-up:** We need `lo` = last sample **≤ start**, hence `bisect_right(start) - 1`; `hi` = first sample **≥ end**, hence `bisect_left(end)`. These bracket an inclusive window.
>   - **Follow-up:** With exact boundaries `[20, 40]`, this picks indices `[1, 2]`. Swapping left/right would unnecessarily pick the outside samples at 0 and 60 ms. For `[25, 45]`, swapping makes no difference because neither boundary exists in the list.
> - `samples[lo:hi+1]` includes 20, 40, 60 ms, providing neighbors around both boundaries.
> - Interpolate at 25 and 45 ms; integrate only 25 → 45, not 20 → 60.
> - Missing neighbors mean no extrapolation: return null integral with a coverage issue.
